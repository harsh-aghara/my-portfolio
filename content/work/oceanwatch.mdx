## The scaling problem

OceanWatch allows users to report coastal hazards. As the volume of reports grew, the map interface became noticeably sluggish. The root cause was the API endpoint serving the viewport data. Every time a user panned the map, the system ran full-table scans to find hazard reports within the new bounding box. This O(n) operation degraded performance directly in proportion to the total number of reports in the database, causing significant latency for simple map interactions.

## PostGIS + GIST index solution

I migrated the spatial queries to leverage PostGIS. By adding a geometry column and applying a GIST index, the database could perform highly optimized bounding box intersections. This structural change replaced the full-table scans with indexed spatial lookups, shifting the query complexity from O(n) to sub-linear time. The map panning immediately became fluid, regardless of the underlying dataset size.

## Transactional integrity

Managing hazard reports required strict data consistency. Deleting a single report meant removing associated comments, media attachments, and audit logs across 7 different tables. I wrapped these bulk operations in standard PostgreSQL transactions to enforce atomicity. If any step failed, the entire operation rolled back. I also implemented an audit logging system to track these administrative actions, ensuring complete visibility and data integrity without leaving orphaned records.
