## What this is

Yoink is a backend system I built to solve a specific problem: how do you sell a limited pool of inventory when thousands of users hit the buy button at the same millisecond? The short answer is that most approaches break, and I had to rebuild the architecture four times before landing on one that actually held up.

The whole thing is Dockerized with Prometheus and Grafana wired in for observability. I used k6 to run load tests across three phases (sustained load, spike, and stress) so every claim has numbers behind it.

## The problem

A flash sale drops a fixed amount of stock and opens it to everyone at once. The naive implementation reads the current stock count, checks if it's above zero, then decrements. Under concurrency, hundreds of requests read the same stock value before any of them write, so you end up selling way more than you have. My baseline benchmark produced 28,486 confirmed orders against 5,000 units of stock.

## How I got to the final architecture

I went through four iterations, each one fixing the previous bottleneck while exposing a new one.

**PostgreSQL row-level locking** fixed the overselling but collapsed under 1,000+ concurrent connections because the connection pool couldn't keep up. **In-memory queuing** moved the bottleneck out of the database but broke as soon as I scaled to multiple Node.js instances. **Redis distributed locks** (Redlock) got close, but TTL edge cases under heavy load still produced a small number of over-orders.

The version that stuck uses **Redis Lua scripts** for the atomic inventory check-and-decrement, combined with **BullMQ** to asynchronously persist orders to PostgreSQL. Redis handles the hot path in a single round-trip with zero race window. The database never sees the burst traffic directly. If a Postgres write fails, a Dead Letter Queue catches it and rolls the stock back into Redis automatically.

## Results

I benchmarked the final system with k6 across three test profiles: sustained 500 req/s for 5 minutes, a spike from 0 to 1,000 req/s in 10 seconds, and a stress test at 1,500 req/s. The p95 latency dropped from 1,390ms (the row-locking version) to 7.6ms. Peak throughput hit 1,459 req/s with a 0% error rate. The DLQ self-healed failed database writes during stress tests without manual intervention. Everything was monitored through Prometheus and Grafana across 3 horizontally scaled instances.

## What I'd change

For a production deployment at larger scale, I'd set up Redis Cluster for multi-region availability. I'd also separate the BullMQ worker pods from the API servers so background processing doesn't eat into response times. And I'd look at NATS JetStream as a potential replacement for BullMQ for higher throughput message brokering.
